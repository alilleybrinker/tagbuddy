# Type system patterns in `tagbuddy`

Notes on the type-level techniques this crate uses, why each one is here, and what it
costs. Written for someone reading the source and wondering "why is it shaped like that",
or borrowing an idea for somewhere else.

Most of these exist to move a class of bug from runtime to compile time, or to stop the
API demanding information it could work out for itself. A few are here because the
obvious version was wrong first — those are marked, because the wrong version is usually
more instructive than the right one.

---

## 1. Generative lifetimes, to make one value distinguishable from another

**The problem.** A tag is an index into a string table. An index from one table means
something else entirely in another, so resolving a tag against the wrong store doesn't
error — it hands back a *different string*. Nothing about the types stops you: two
`Storage` values have the same type, so their tags do too.

**The technique.** Each `Storage` carries an invariant lifetime, unique to that value:

```rust,ignore
pub struct Storage<'brand, L = DefaultLabel, K = Spur, H = RandomState>(
    Arc<Interner<K, H>>,
    PhantomData<L>,
    Id<'brand>,
);
```

`Id<'brand>` comes from [`generativity`], and is a zero-sized
`PhantomData<fn(&'id ()) -> &'id ()>`. Two properties matter:

- **Invariance.** `fn(T) -> T` is invariant in `T`, so `'brand` can never be coerced to
  another lifetime. Two brands can't unify, ever. A covariant marker like
  `PhantomData<&'id ()>` would let the compiler shorten one to match another, and the
  whole thing would silently do nothing.
- **It's still `Send`/`Sync`.** A function pointer is both. The other common invariance
  marker, `PhantomData<Cell<&'id ()>>`, is *not* `Sync`, which would have made every
  `Storage` thread-hostile — an easy way to lose a property you weren't thinking about.

`make_guard!` produces a `Guard<'brand>` whose lifetime cannot be named or reused, using a
drop-timing trick; a `Storage` constructor consumes one. Every tag copies the brand of the
storage that interned it, so crossing them fails to compile.

**What it costs.** A lifetime parameter on `Storage`, `Tag`, `Parser`, `TagManager` and
everything generic over them. Values can't outlive their guard's scope, and branded types
can't be stored in the same struct as the data they borrow. That's the real price, and it
bought the crate's central guarantee, so it was worth paying here — but it is not free and
shouldn't be reached for casually.

[`generativity`]: https://docs.rs/generativity

## 2. A phantom parameter is only as strong as its weakest constructor

This is the part that's easy to get wrong, and the crate did get it wrong.

The brand only means something if a `'brand` can't be attached to a store that didn't mint
it. That makes **every constructor** part of the guarantee. Each way to obtain a
`Storage<'brand, ..>` must either consume a `Guard<'brand>` or derive from an existing
storage over the same interner:

| Constructor | Brand |
|---|---|
| `fresh`, `unique`, `shared`, `fresh_with_*` | consumes a `Guard` |
| `share_as`, `try_share_as` | inherits, same interner |
| `deep_clone` | consumes a *new* `Guard`, because it's a different interner |

A `Default` impl would have handed out a `Storage<'brand>` for whatever `'brand` the caller
could name. So would `From<StringInterner>`. Both existed; both had to go. `Default` in
particular looks completely innocuous.

Two more leaks found later, both in code that had nothing obviously to do with brands:

- **`DerefMut` to the inner `Arc`** let you write `*storage = other_arc`, swapping the
  interner while the brand stayed put. A tag interned as `"hello"` then resolved to
  `"decoy"`.
- **`Storage::shared` taking a bare handle** minted a *new* brand for an interner that
  already had one, so tags from the original couldn't be used with it — the opposite
  failure, over-strictness rather than unsoundness. `try_share_as` fixes it by checking
  `Arc::ptr_eq` and adopting the existing brand when the handle really is the same
  allocation.

**The lesson worth carrying:** when a phantom parameter encodes an invariant, audit the
constructors *and* the trait impls as one surface. `Deref`, `DerefMut`, `Default`, `From`,
`Clone` are all constructors for this purpose.

## 3. One marker per job

The crate has two markers that look similar and do different things:

- **`'brand`** — *storage identity.* Enforced by the compiler. Prevents resolving a tag
  against the wrong interner.
- **`Label`** — *vocabulary separation.* A convention. Keeps "post tags" and "ratings"
  distinct at the type level even when they deliberately share one interner via
  `share_as`.

They were originally one thing — `Label` alone, documented as giving "the compile-time
guarantee that a `Tag` generated by one `TagManager` is never resolved through another".
It didn't. Two `Storage::fresh()` calls produced independent interners carrying the same
label, and a tag from one resolved through the other to a different string, silently.

The conflation is what hid the bug: `Label` genuinely delivered the vocabulary half, so
the storage-identity half looked delivered too. Splitting them made the gap obvious and
gave each a mechanism suited to it — a lifetime for the thing that must be enforced, a
type parameter for the thing that's a naming convention.

## 4. Projecting parameters instead of restating them

`TagManager` used to take six parameters:

```rust,ignore
TagManager<'brand, Tags, Spur, PlainTag<'brand, Tags>, Plain<Tags>>
```

Note `Tags` three times. Given the parser, everything else follows: the tag type is
`P::Tag`, and the label and key are that tag's own associated types. Only the parser and
the hasher were ever free choices:

```rust,ignore
TagManager<'brand, Plain<Tags>>
```

The field types use projections (`LabelOf<'brand, P>`, `KeyOf<'brand, P>`), which are also
public for when a caller needs to name one.

**The general rule:** if `B` is determined by `A`, don't take both. The caller can't
supply a `B` that disagrees — the bounds reject it — so all the second parameter does is
give them something to get wrong, and something to type.

## 5. Bundling parameters behind associated types

Same problem, harder instance. `Index` needed a manager, and naming one meant naming all
its parameters:

```rust,ignore
Index<'m, 'brand, 'items, L, K, T, P, H, I>   // nine
```

Call sites inferred all of it, so this only hurt in a struct field or a return type —
which is exactly where a long-lived index lives.

`ManagerParts` collapses it:

```rust,ignore
pub trait ManagerParts: sealed::Sealed {
    type Key: Key + Hash;
    type Tag;

    fn lookup(&self, raw: &str) -> Option<Self::Key>;
    fn text(&self, key: Self::Key) -> &str;
    fn parts_of(tag: &Self::Tag) -> TagParts<'_, Self::Key>;
}
```

giving `Index<'m, 'items, M, I>` — four.

Two details make it work, and both are the interesting part:

**The trait has no `'brand` parameter.** `type Tag` is just the manager's tag type, and
*that type already carries its own brand*. So `<Mgr<'b> as ManagerParts>::Tag` projects to
`PlainTag<'b>` without the trait ever naming `'b`. An associated type can carry a lifetime
that comes from `Self` without the trait declaring it — which is what keeps the bundle
from reintroducing everything it removed.

**It exposes operations, not the storage.** The obvious design is
`fn storage(&self) -> &Storage<'brand, ..>`. That signature names the brand, so the trait
would need a lifetime, so the bundle would be pointless. Exposing the three things the
query engine actually does instead keeps the lifetime out. `parts_of` is an associated
function for the same reason: calling `Tag::parts` would require the bound
`Self::Tag: Tag<'brand>`.

The trait is sealed. Nothing else could sensibly be "the parts of a manager", and sealing
keeps it free to change.

## 6. Dropping a lifetime that only stated a bound

`Tagged` used to be `Tagged<'brand, T: Tag<'brand>>`. The lifetime existed only so the
bound on `T` could be written.

That's not free: it appears in every impl, and in every bound that mentions the trait. It
also blocked §5 outright — once a manager's parameters are bundled, there's no `'brand`
available to write `I: Tagged<'brand, M::Tag>` with.

Dropping the bound gives `Tagged<T>`. Impls become
`impl<'brand> Tagged<PlainTag<'brand, Tags>> for BlogPost<'brand>`, and code that needs
`T` to really be a `Tag` says so itself. The blog test still implements it twice for two
tag vocabularies, so the disambiguation the tag type provides is unaffected.

**The rule:** a parameter that exists only to state a bound is usually better stated at
the use site. Bounds on trait *declarations* are rarely load-bearing; they mostly move
work from one place to every other.

## 7. Making a property structural rather than enforced

The brand says a key came from *this* interner. It doesn't say the key is still valid —
that needs the interner to never remove anything.

Rather than police this, the crate picked a type that can't do otherwise.
`lasso::ThreadedRodeo` has **no `&mut self` method at all**, and no `clear`, `remove` or
`truncate`; `Storage` holds it behind an `Arc` with no `DerefMut`, and `handle()` returns
`&Arc`, so `Arc::get_mut` is unreachable. Append-only isn't a rule anyone follows — it's a
shape with no other option.

Worth noting what the actual risk was, because it was mis-stated at first: the *previous*
interner had no removal method either. The invalidation route was always wholesale
replacement through a `&mut` — assignment, `mem::swap`, `mem::take`. So the fix is
refusing to hand out `&mut`, not restricting a method surface. When auditing "can this be
invalidated", look at what the *container* permits, not just what the type's own methods
offer.

## 8. Two invariants can delete an error type

Put §1 and §7 together:

- the brand says the key came from this interner, and
- append-only says the key is still there,

so resolving a tag cannot fail. Not "rarely fails" — there is no failure case. `resolve_tag`
returns `String`, and `ResolveError` was deleted from the crate: every one of its variants
(`TagNotFound`, `KeyNotFound`, `ValueNotFound`, `PartNotFound`) had become unreachable.

Going lock-free removed the rest. `ThreadedRodeo` interns and resolves through `&self`, so
there's no `Mutex`, so no poisoning, so `StorageError` and `ParseError::StorageError` went
too — along with `StorageLock` and a chunk of machinery in the batch methods that existed
only to take a lock once rather than per tag.

**The pattern:** an error variant is often the residue of a missing invariant. Worth asking
of any `Result`-returning function whether the failure is intrinsic or just unproven.

## 9. Inference is part of the signature

`TagManager::new(guard, parser)` looks obviously correct and did not compile at the call
site.

`new` creates the storage itself, so the storage's label is determined by the parser — and
the parser's label by nothing at all. `TagManager::new(guard, Plain::new())` had no way to
pick `L`. The type checked; it was just unusable without an annotation naming a type the
caller had no reason to think about.

The fix constrains `new` to the default label and key. That makes it inferable, and it
happens to draw the line where the design already draws it: labels exist so two managers
can share an interner, which needs the builder and an explicit `Storage` anyway. The blog
test failed to compile on `new` for exactly this reason — it has a labelled manager — and
now demonstrates both paths.

**The rule:** a parameter nothing constrains is a parameter the caller must annotate. When
adding a convenience constructor, check what it removes from the inference context, not
just what it removes from the call.

## 10. `unsafe` is not a documentation mechanism

`Label` used to be an `unsafe trait`, and its own docs admitted why:

> There aren't actual safety concerns around its use […] but it's marked `unsafe` to hint
> toward the special guarantees around the marker trait.

The obligation it was gesturing at — one label per interner — is now the brand's job,
enforced by the compiler rather than asked of implementors. So the `unsafe` came off.

An `unsafe` trait in a public API tells a reader there's a memory-safety obligation to go
find. Using it for emphasis spends that signal on nothing, and makes the real ones harder
to take seriously.

Related, in the other direction: this crate also carried hand-written
`unsafe impl Send`/`Sync` for `TagManager` that were *actually unsound* — unconditional in
the backend and hasher parameters, so a manager holding an `Rc`-bearing hasher claimed
`Send`. Removing them left auto-derivation, which gets it right: the default manager is
still `Send + Sync`, and the `Rc` case now correctly fails to compile. Hand-written
`unsafe impl`s of auto traits deserve suspicion in proportion to how generic the type is.

## 11. Verifying a type-level guarantee

A guarantee that lives in the type system needs a test that lives there too, and this is
harder than it looks.

**`compile_fail` doctests prove almost nothing on their own.** They assert that a block
failed to compile — not *why*. Rustdoc does not verify the error code even when you supply
one: a block annotated with `E0999`, which is not a real error code, passes. So a
`compile_fail` test can be passing because of a typo, a missing import, or an inference
ambiguity, while the property it claims to check has quietly stopped holding.

Two things make them trustworthy here:

1. **Pair each with a compiling twin.** Every `compile_fail` block in this crate sits
   beside an example identical except for the one thing under test — usually which manager
   resolves the tag. Since the twin compiles, the difference is the only candidate
   explanation for the failure.
2. **Check the error once, by hand.** Each was extracted into a real test file and
   compiled to confirm it fails with `E0716` — the brand — rather than something
   incidental.

**For runtime properties, make the test fail on purpose.** The query engine has two
execution strategies that must agree, checked by generating ~300 queries and comparing
both paths. That test is only worth having if it can fail, so: introducing the specific
bug it exists to catch (treating `Match::All` candidates as exact when they're a superset)
was confirmed to break it. A test that has never failed is a hypothesis, not a test.

## 12. Small things

**Niche optimization is free API quality.** Keys are `NonZeroU32`, so `PlainTag` is 4 bytes
and `Option<PlainTag>` is *also* 4. Worth knowing when choosing a key representation —
picking `u32` over `NonZeroU32` would silently cost a word in every `Option`.

**RPIT lifetime capture has two fixes, and the boring one is usually better.** Returning
`impl Iterator<Item = &'s str> + 's` from a method on a branded type fails: the closure
captures `'brand`, which the bound doesn't name. Precise capturing (`+ use<..>`) works but
raises the MSRV and has to list every type parameter. The alternative is to capture less —
dereference to the interner, whose type has no brand in it, so the closure never sees the
lifetime. Reach for `use<>` when the capture is genuinely needed, not to paper over
capturing more than you meant to.

**Sealed traits.** `ManagerParts` is sealed via a private supertrait. It's public because
users write it in bounds, but nothing outside the crate could implement it meaningfully,
and sealing keeps its three methods free to change.

## What this cost overall

Honesty requires the other column:

- Every branded type has a lifetime parameter, and values can't escape their guard's
  scope.
- The crate is pinned to Rust 1.85, entirely because `generativity` uses edition 2024.
- Memory is never reclaimed, which is what append-only means. Compaction is copying into
  a fresh store, and the brand makes sure old tags can't follow the data across.
- `Index` borrows its items, so it can't be stored alongside them, and it's rebuild-only.

The trade was worth it for a crate whose entire premise is cheap interned handles — the
handles are exactly the thing that's dangerous to mix up. It would not obviously be worth
it for a crate whose values carry their own meaning.
